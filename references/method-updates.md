# 开放的方法更新机制

本技能接受对话中的新方法、项目实践和组会指导，持续提炼、检验与更新。当前结构是可修正的工作版本，不是封闭标准。

## 更新来源与状态

- 用户明确提出规则校准或要求加入的方法：在本次已授权的技能范围内直接更新，并说明改了什么；不重复请求许可。
- 组会纪要、导师意见、录音与修订批注：提取原意、所针对的问题和建议的改变，区分材料中的意见与用户此次任务。用户要求据此更新时执行；只要求总结时先交总结与拟议修改。
- 探索性想法或证据不足的方法：标记候选、适用条件和验证动作，不直接升为默认通则。
- 单个项目的定位、数字、地方安排：留在项目基线；只有能够说明跨项目适用条件的方法才进入通用部分。

指导者的判断同样需要事实与论证，不能只因权威来源就压过证据。来源冲突时，说明各自前提、影响和待确认处；用户最新明确校准优先于旧偏好，但事实不能为适配意见而改写。

## 一次更新的操作

1. 提取新方法：原话或准确转述、来源、日期、想解决的问题。
2. 对照当前方法：新增、补充、替代、限缩还是纠错，哪些条款和工作流受影响。
3. 确定范围：通用规则、某类报告、某一阶段或单项目；明确成立条件和未知项。
4. 修改相关方法文件，并同步主入口、路由、模板与检查项，避免新旧要求同时生效而冲突。
5. 按改动检查结构和内部链接；影响实际行为时增加或调整案例，区分规则覆盖检查与真正运行过的测试。
6. 在现有项目记录或变更记录中说明更新结果。存在分发包时同步重建，报告版本或修订日期，不宣称已安装或发布。

## 更新记录字段

日期、来源、原问题、新方法、适用范围、证据状态、修改位置、被替代条款、验证情况和待观察结果。记录保留可追溯性；无需把私人组会原文或客户数据装入公开技能包。

使用一段时间后，根据真实产物、用户反馈和反例判断保留、调整或撤回。新规则应改善判断或执行，避免无效增加字数、表格或固定约束。

## 会话内版本刷新规则

1. 首次使用记录实际加载的技能目录与metadata.version。权威来源采用用户明确指定的目录，否则采用本次环境实际提供的技能目录；本地开发副本、安装副本和历史压缩包不默认互相同步。
2. 同一项目每轮开始时轻量读取该目录的SKILL.md版本字段，对照已加载版本；较长任务中若收到技能更新提示，在下一安全步骤前再检查。不需反复全文读取或持续轮询。
3. 已知同一技能存在多个获准使用的版本时，按主版本、次版本、修订号数值比较，采用最新适用版本；例如0.3.0晚于0.2.0，0.10.0晚于0.9.0。不按字符串顺序或文件名猜测。不搜索无关目录或自动下载、安装、覆盖其他副本。用户明确锁定版本时遵守锁定。
4. 发现新版本后重新读取SKILL.md及当前任务所需参考，核对变更影响。旧规则被新版本替代的部分停止使用；未受影响的方法继续。版本号相同但用户提示已修改、修订记录或文件变化表明有更新时，也刷新相关文件，避免快速迭代漏升版本。
5. 保留短长期目标、来源证据、数据口径、已确认决策和完成状态。新方法影响旧结论时标记待复核并说明原因，不静默重写事实或把任务退回起点。向用户简短说明已切换的版本及实质影响，无变化不反复播报。
6. 版本缺失或格式不明时标记未知，读取当前权威入口确认方法；目录出现降版或来源不清时不自动认定为更新，检查是否明确回滚。无法读取新版时说明限制，继续可安全完成的部分，不宣称已加载或采用了新版。
7. 在既有项目状态中记录实际使用目录、版本、检查时间和本轮受影响的方法，便于下一轮及上下文恢复后继续。

技能文本被加载并执行时才能实施上述检查；旧版本若没有此规则，不会自行获知它。新目录中的版本也不会自动覆盖仍在使用的旧安装副本，需要用户或环境明确提供其位置。本规则不等同于自动升级或安装功能。


## 版本号更新规则

采用主版本.次版本.修订号三个非负整数，例如0.3.1。SKILL.md的metadata.version是版本号唯一权威字段；README、变更记录与分发包名称同步引用该值。版本大小按整数逐段比较。

| 级别 | 何时更新 | 示例 |
|---|---|---|
| 修订号PATCH | 不改变任务边界和主要交付结构的纠错、歧义澄清、局部问句或示例改善、引用与文档修复 | 0.3.0→0.3.1 |
| 次版本MINOR | 新增可复用方法、工作流、研究维度或实质行为规则；在0.x阶段也用于不兼容变化，须明确迁移影响 | 0.3.1→0.4.0，修订号归零 |
| 主版本MAJOR | 1.0以后，对既有任务适用范围、关键流程或交付契约作不兼容改变，旧用法必须迁移 | 1.4.2→2.0.0，次版本和修订号归零 |

0.x表示仍在探索和迭代，不承诺兼容性；从0.x进入1.0是成熟度决定，不按修改次数或日期自动晋级。进入1.0前应确认主要工作流、交付契约和来源维护方式稳定，完成有代表性的真实使用或行为验证，并由用户明确决定。版本号不是质量评分，结构检查通过不代表方法有效性已验证。

### 更新单位与同步步骤

1. 一项已授权且完成交付的Skill修改形成一个修订批次，按本批次最高影响级别升一次；连续工具操作与中间草稿不逐次升号。只有讨论、待审阅候选、项目事实或包外协作记录变化时不升Skill版本。
2. 默认在当前修改授权内判断级别并同步版本，无需每次询问。用户明确指定版本或要求暂不升号时遵守，并说明由此产生的版本识别限制。实质方法增加不能仅以改动文件少为由降为PATCH。
3. 更新metadata.version，同步README与[变更记录](../CHANGELOG.md)。记录日期、内容、兼容性或迁移影响、验证结果；不把私人案例内容写进公开记录。
4. 对本次修改进行相关检查，通过后按权威版本号生成压缩包。交付过的版本包保留，不用不同内容覆盖同版本包；校验后未变化的重复交付直接复用。错误修复生成新PATCH包，不删除历史版本。
5. 若撤回有问题的方法，通常发布更高版本的修复并说明回退了什么；用户显式锁定旧包时可使用旧包，但不把它称为新版。不混用旧入口与新参考文件。
6. 版本变更后执行会话内刷新，记录实际加载版本。打包或更新本地草案不等于已经安装或公开发布。

本规则从0.3.0开始执行。此前0.2.0曾在同号下持续更新，现有历史包只代表最后一次同号内容，不能声称保存了此前所有修订快照。会话刷新中的同号变化检测作为兼容兜底保留，后续正常交付按本规则升号。
